## Краткий вывод
Проект рабочий как MVP, но сейчас в нем есть несколько критичных проблем: часть настроек не применяется без перезапуска, в Docker база смонтирована неверно, есть ошибки в UX/логике Telegram-обработчиков, отсутствуют тесты и базовая инженерная обвязка. Перед развитием функционала стоит стабилизировать основу.

## Основные проблемы

### P0 — критично исправить в первую очередь
1. **База данных в Docker подключена неконсистентно**  
   `database.py` использует `prices.db` в корне `/app`, а `docker-compose.yml` монтирует `/app/prices_data/prices.db`. В текущем виде volume не гарантирует сохранность реальной БД.

2. **Изменение интервала проверки не применяется на лету**  
   В настройках интервал сохраняется в БД, но job в `APScheduler` не пересоздается. Пользователь видит, что интервал изменен, но фактически он меняется только после рестарта.

3. **Ручной ввод порога работает неверно**  
   В `process_threshold()` значение `threshold` валидируется, но при `db.add_product(...)` не передается; будет использован дефолт `500`.

4. **Некорректный возврат в главное меню из callback**  
   `process_back_to_main()` вызывает `edit_text(..., reply_markup=get_main_keyboard(...))`, но для `edit_text` допустима inline-клавиатура, не `ReplyKeyboardMarkup`.

5. **Удаление товара не очищает историю и не проверяет факт удаления**  
   `delete_product()` всегда возвращает `True` после `commit()`, даже если запись не удалена. История цен остается сиротой.

### P1 — важные улучшения надежности
6. **Смешение слоев и перегруженный `bot.py`**  
   В одном файле находятся: Telegram handlers, scraping, графики, scheduler, middleware, логирование.

7. **SQLite используется синхронно внутри async-бота**  
   Все вызовы БД блокируют event loop. Пока объем небольшой, но при росте числа товаров начнутся задержки.

8. **Парсинг Яндекс.Маркета хрупкий**  
   Жесткие CSS/data-auto селекторы, нет fallback-логики, retry/backoff, контроля антибот-защит.

9. **Проверка цен выполняется последовательно**  
   Все товары обходятся по одному; время цикла будет линейно расти.

10. **Нет проверки владения товаром в ряде сценариев чтения**  
   `get_product(product_id)` не фильтрует по `user_id`. Для закрытого админ-бота риск ограничен, но при нескольких администраторах возможны пересечения данных.

### P2 — качество и сопровождение
11. **Документация расходится с кодом**  
   В README описаны команды `/list`, `/delete`, `/threshold`, но фактический интерфейс в основном кнопочный. Не описан `ADMIN_IDS`.

12. **Лишний/мертвый код**  
   `create_tables()` дублирует `init_db()`, в `database.py` блок `if __name__ == "__main__": init_db()` некорректен, есть неиспользуемые импорты.

13. **Логирование без ротации и с инициализацией на импорте**  
   Возможен бесконтрольный рост файлов логов и дублирование handlers.

14. **Нет тестов, линтеров, CI**  
   Нет защиты от регрессий.

15. **В репозитории присутствует локальная БД как артефакт разработки**  
   Для проекта лучше хранить шаблон/миграции, а не runtime-файл как часть рабочего дерева.

## Этап 1. Стабилизация production-базы и runtime
**Цель:** устранить ошибки, влияющие на сохранность данных и фактическую работу бота.

Задачи:
1. Вынести путь к БД в переменную окружения, например `DATABASE_PATH`.
2. Привести Dockerfile и `docker-compose.yml` к одному пути хранения, например `/app/data/prices.db`.
3. Исправить изменение интервала проверки:
   - хранить ссылку на scheduler/job;
   - при изменении интервала делать `reschedule_job` или пересоздавать job.
4. Исправить добавление товара с ручным порогом.
5. Исправить `back_to_main`: не использовать `ReplyKeyboardMarkup` в `edit_text`, а отправлять новое сообщение.
6. Исправить `delete_product()`:
   - проверять `rowcount`;
   - удалять `price_history` или включить `ON DELETE CASCADE`.

Критерий готовности:
- БД реально сохраняется между рестартами контейнера.
- Интервал проверки меняется без перезапуска.
- Ручной порог сохраняется корректно.
- Удаление товара полностью очищает связанные данные.

Критерий готовности:

- Ошибки сети и разовые сбои не ломают цикл проверки.

## Этап 4. Безопасность и модель доступа
**Цель:** исключить утечки и пересечение пользовательских данных.

Задачи:
1. Во всех операциях чтения/изменения товара учитывать `user_id`.
2. Явно обработать сценарий пустого `ADMIN_IDS`.
3. Не логировать лишние чувствительные данные.
4. Проверить `.env.example` вместо реального `.env` в документации.

Критерий готовности:
- Пользователь может видеть и менять только свои товары.
- Конфигурация запуска воспроизводима без доступа к приватным данным.

## Этап 5. Исследование авторизации без «живых» cookie
**Цель:** понять, можно ли отказаться от постоянного хранения и ручного обновления `YA_COOKIE`, сохранив при этом доступ к цене именно для нужного аккаунта.

Контекст:
- Сейчас проект зависит от `YA_COOKIE` и фактически использует живую браузерную сессию.
- Для Яндекс.Маркета цена, скидки, кэшбек, персональные условия и наличие могут отличаться в зависимости от аккаунта, региона, подписки и состояния авторизации.
- Поэтому полный отказ от account-bound контекста может быть невозможен: это действительно может оказаться «вынужденным злом».

Задачи исследования:
1. Зафиксировать, какие именно данные зависят от аккаунта:
   - базовая цена;
   - цена по акции;
   - цена с Плюсом/баллами/персональной скидкой;
   - региональная доступность;
   - seller-specific offer.
2. Проверить альтернативы живым cookie:
   - официальные API Яндекса/Маркетплейса, если применимо;
   - публичные неавторизованные endpoints;
   - headless-browser flow с периодическим получением свежей сессии;
   - хранение refreshable session state вместо сырой cookie-строки;
   - прокси-слой/внешний scraper service.
3. Оценить вариант «авторизация через отдельный технический аккаунт»:
   - насколько цена будет соответствовать целевому аккаунту;
   - какие персональные скидки будут потеряны;
   - приемлемо ли это для бизнес-цели.
4. Исследовать безопасное хранение сессии:
   - шифрование секретов;
   - ротация;
   - срок жизни;
   - минимизация логирования;
   - разделение per-user / shared-account модели.
5. Принять архитектурное решение по одной из моделей:
   - **A. Оставляем cookie как временное решение** и улучшаем безопасность/ротацию;
   - **B. Переходим на технический аккаунт** и принимаем менее точную персонализацию;
   - **C. Автоматизируем обновление session state** через браузерный сценарий;
   - **D. Разделяем два режима:** публичная цена без логина и персональная цена с авторизацией;
   - **E. Храним и показываем обе цены одновременно:** публичную цену и цену под аккаунтом, а также их расхождение.

Таблица сравнения вариантов:

| Вариант | Точность цены для конкретного аккаунта | Сложность реализации | Риск блокировок/антибота | Безопасность | Стоимость поддержки | Комментарий |
|---|---|---:|---|---|---|---|
| Живые cookie вручную | Высокая | Низкая | Средний/высокий | Низкая | Средняя | Самый быстрый старт, но плохая операционная устойчивость |
| Технический аккаунт | Средняя | Низкая/средняя | Средний | Средняя | Средняя | Подходит только если персональные цены не критичны |
| Публичная цена без логина | Низкая/средняя | Низкая | Низкий/средний | Высокая | Низкая | Хорошо как fallback, но не отражает персональные условия |
| Официальный API / партнерский API | Средняя/высокая* | Высокая | Низкий | Высокая | Средняя | Нужно отдельно проверить доступность нужных данных и условий использования |
| Автообновление session state через browser flow | Высокая | Высокая | Высокий | Средняя | Высокая | Ближе всего к реальному аккаунту, но дорого и хрупко |
| Внешний scraper service | Зависит от реализации | Средняя/высокая | Средний/высокий | Средняя | Высокая | Переносит сложность наружу, но не убирает ее |
| Dual-mode: публичная + авторизованная цена | Высокая в auth-режиме / средняя в public | Средняя | Средний | Средняя/высокая | Средняя | Практичный компромисс для развития продукта |
| Две цены одновременно: public + account | Высокая | Средняя/высокая | Средний | Средняя | Средняя/высокая | Позволяет видеть персональную выгоду и снижает зависимость от одного источника |

\* если API вообще отдает именно те цены/скидки, которые нужны бизнесу.

Артефакты исследования:
- таблица сравнения вариантов;
- список зависимых от аккаунта полей цены;
- решение по модели хранения авторизации;
- риски: блокировки, антибот, юридические и эксплуатационные ограничения.

Дополнительная продуктовая гипотеза:
- Для пользователя может быть наиболее полезен режим, где бот хранит **две цены на один и тот же товар**:
  - **публичную цену** без авторизации;
  - **персональную цену** в контексте аккаунта.
- Это позволит:
  - понимать, есть ли реальная выгода от авторизованного состояния;
  - видеть разницу между «общей» и «моей» ценой;
  - использовать публичную цену как fallback, если авторизованная сессия временно недоступна.

Что проверить в исследовании для этой модели:
1. Можно ли стабильно получать обе цены для одного SKU/URL.
2. Как хранить две временные серии в БД:
   - `public_price`;
   - `account_price`;
   - `price_delta` между ними.
3. Какие уведомления полезнее:
   - изменение публичной цены;
   - изменение персональной цены;
   - изменение разницы между ними.
4. Как это отображать в UX:
   - карточка товара: «Публичная / Моя цена»;
   - графики по двум сериям;
   - уведомление вида: «Публичная цена 54 990 ₽, ваша цена 49 990 ₽, выгода 5 000 ₽».

Критерий готовности:
- Понятно, можно ли уйти от живых cookie без потери бизнес-ценности.
- Если нельзя, зафиксирован безопасный и операционно приемлемый способ работы с авторизованной сессией.
- Отдельно принято решение, нужен ли продукту dual-price режим как основной сценарий.
